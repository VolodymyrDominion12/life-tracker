# Life Tracker

Локальний трекер життя: **фінанси → калорії → спорт → навчання**, зі статистикою,
аналітикою та повним експортом/імпортом. Без сервера, без акаунтів, без мережі —
усі дані у SQLite-файлі на пристрої.

Стек: **Expo SDK 57 (React Native) + TypeScript + expo-sqlite + Drizzle ORM**, десктоп
потім — через Tauri. Концепція й обґрунтування вибору — у [`docs/CONCEPT.md`](docs/CONCEPT.md).

## Ключові рішення

**1. Гроші — цілі числа в копійках.** Ніяких `float`: 0.1 + 0.2 ≠ 0.3, і в обліку
це накопичується у видимі розходження.

**2. Адаптер сховища `RawDb` — не абстракція заради абстракції.** Вузький інтерфейс
(виконати SQL, отримати рядки, транзакція) реалізують:
`expo-sqlite` на пристрої, `node:sqlite` у тестах, за потреби — `tauri-plugin-sql`
на десктопі. Саме тому 269 перевірок виконуються в Node без емулятора й без телефона.

**3. Міграції — власний раннер на `PRAGMA user_version`.** Версія схеми лежить у
заголовку самої бази, тому міграція і зміна версії відбуваються в одній транзакції:
або застосувалося все, або нічого. Жодного зв'язку з кодогенерацією.

**4. Drizzle — для записів, SQL — для аналітики.** Типізація критична там, де
формуються значення. Агрегації живуть у VIEW, і дублювати їх конструктором запитів
означало б мати дві різні логіки підрахунку тих самих чисел.

**5. Мітки часу — тільки ISO-8601 UTC.** Не косметика: LWW-злиття при імпорті
порівнює `updated_at` як рядки, тож `datetime('now')` (формат `YYYY-MM-DD HH:MM:SS`)
ламає порівняння. Це вже був реальний баг — його спіймав `npm run verify`, і саме
тому в сідах тепер `strftime('%Y-%m-%dT%H:%M:%fZ','now')`.

**6. М'яке видалення.** `deleted_at` замість `DELETE` — щоб синхронізація між
пристроями колись додалася без переписування схеми.

**7. Швидкий ввід понад усе.** Головний ризик трекера — закинути його через
тиждень. Тому Quick Add відкривається одною кнопкою, пам'ятає останні категорії,
не закривається після збереження (можна вводити кілька записів підряд) і не
вимагає жодного обов'язкового поля, крім суми/тривалості.

**8. Проценти за кредитом не зберігаються — вони рахуються.** У базі лежать лише
умови (джерело, дата, сума, ставка з періодом) і погашення. Залишок, набіглі
проценти й прострочення виводяться з них на будь-яку дату функцією
`computeLoanState` (`src/domain/loan-accrual.ts`). Причина проста: похідне число,
записане в базу, після першої ж правки ставки чи дати платежу стає неправдою, а
двох правд про один борг не буває. Тому ж SQL не має своєї копії цієї формули —
агрегації в VIEW лишились лише там, де вони справді незалежні.

**9. Ставка зберігається у двох виглядах.** `rate_value` + `rate_period` — те, як
її назвав кредитор («0,5% у день»), `annual_rate` — вона ж, приведена до річних
за банківською конвенцією 30/360 (місяць = 30 днів, рік = 360). Без нормалізації
«2%» у місяць і «18%» річних виглядали б як числа одного порядку, і сортувати
кредити за дорожнечею було б неможливо. Нарахування — простий процент за
фактичну кількість днів на залишок тіла; платіж спершу закриває проценти, потім
тіло, а надлишок лишається авансом.

## Експорт та імпорт

**JSON — повний бекап.** Усі 18 таблиць, версія схеми, час експорту. Файл пишеться
в кеш застосунку і надсилається через системне «Поділитися» (Google Drive, Telegram,
пошта).

**CSV — по таблиці**, для Excel та Python: транзакції, харчування, тренування,
навчання, платежі за кредитами. Суми подано і в копійках (`*_minor`), і у звичайних
одиницях. Кодування UTF-8 з BOM (щоб Excel не ламав кирилицю), екранування за
RFC 4180, кома як розділювач.

**Імпорт — злиття, а не заміна:**

- рядки зіставляються за первинним ключем (UUID, згенерований на клієнті);
- перезапис відбувається лише якщо у файлі `updated_at` не старіший за локальний
  (last-write-wins) — інакше локальна правка була б затерта;
- рядки, яких немає у файлі, **не видаляються**;
- колонки, яких немає в поточній схемі, ігноруються, а не ламають імпорт;
- усе в одній транзакції: часткового імпорту не буває (перевірено тестом).

## Що далі, за пріоритетом

1. **Запустити на телефоні** й виправити те, що вилізе в UI (єдине, що не перевірено).
2. **Цілі й серії** (streaks) на екрані «Сьогодні» — таблиця `goals` уже є.
3. **Каталог їжі**: сканер штрихкоду + Open Food Facts з офлайн-кешем.
4. **Десктоп через Tauri**: той самий код, інший рушій БД за тим самим `RawDb`.
5. **Синхронізація** (PowerSync/ElectricSQL) — тільки якщо реально захочеться
   кілька пристроїв. Схема до цього вже готова (UUID, `updated_at`, `deleted_at`).

Зроблене по кредитах (можна розвивати): погашення можна прив'язати до транзакції
по рахунку (`loan_payments.account_id` і `transaction_id` уже в схемі) — тоді
платіж автоматично зменшував би залишок на картці, а не жив окремо.

## Відомі обмеження

- **Web-версія** вимагає заголовків COOP/COEP від хостингу (обмеження WASM-SQLite),
  тому `npm run web` — для розробки, а не як готовий продукт.
- **Транзакції-перекази** підтримані у схемі й аналітиці (знакові суми), але у
  Quick Add їх ще немає — тільки витрата й дохід.
- **Курси валют** задаються вручну в таблиці `currencies`; автоматичного оновлення
  немає (свідомо: це мережа, а застосунок поки повністю офлайн).
- **Кореляції** в аналітиці — орієнтир, а не висновок: на 20–40 точках значущість
  майже ніколи не досягається, тому в тексті прямо написано, що це не причинний зв'язок.

## Нотатки про середовище цієї машини

Проблеми, які виникали під час збірки — усі три стосуються оточення, а не коду:

1. **Кеш npm містить файли, що належать root** (наслідок колись запущеного
   `sudo npm`). Через це `npm install` падає з `EACCES`. Я використав локальний кеш
   (`npm_config_cache`), але правильне лікування:
   ```bash
   sudo chown -R 1000:1000 ~/.npm
   ```
2. **`npx expo start` не запускався тут**, бо Expo CLI пише свій конфіг у `~/.expo`,
   а доступ за межі робочої теки обмежений політикою середовища. Зі свого термінала
   це не проблема — команда створить теку автоматично.
3. **Metro падає з `ENOSPC: System limit for number of file watchers reached`.**
   Це не помилка застосунку й не щось, що лікується в коді: ядро Linux обмежує
   кількість inotify-вотчерів на користувача, а Metro без Watchman вішає окремий
   вотчер на **кожну теку** проєкту — разом із `node_modules`, де таких тек 5745.
   На машинах зі старим типовим лімітом `8192` цього не вистачає (у CI-контейнерах
   із чистим user-namespace ліміт вищий, тому там збірка проходить).

   Перевірити й полікувати (у своєму терміналі, потрібен `sudo`):
   ```bash
   # скільки зараз — і хто винен, якщо не Metro
   cat /proc/sys/fs/inotify/max_user_watches
   sudo python3 - <<'PY'
   import glob, collections
   tot = collections.Counter()
   for f in glob.glob('/proc/[0-9]*/fdinfo/*'):
       try: t = open(f).read()
       except OSError: continue
       n = t.count('inotify wd:')
       if n: tot[f.split('/')[2]] += n
   for pid, n in tot.most_common(5):
       cmd = open(f'/proc/{pid}/cmdline','rb').read().replace(b'\0', b' ').decode()[:60]
       print(f'{n:>7}  pid={pid}  {cmd}')
   print('усього вотчерів:', sum(tot.values()))
   PY

   # підняти ліміт (вистачає з запасом на будь-який node_modules)
   sudo sysctl -w fs.inotify.max_user_watches=524288
   sudo sysctl -w fs.inotify.max_user_instances=1024

   # зробити постійним
   printf 'fs.inotify.max_user_watches=524288\nfs.inotify.max_user_instances=1024\n' \
     | sudo tee /etc/sysctl.d/99-inotify.conf
   sudo sysctl --system
   ```
   Альтернатива — `sudo apt install watchman`: Metro тоді використовує один демон
   замість вотчера на кожну теку (швидше й менше вотчерів), але ліміт усе одно
   варто підняти. IDE (PyCharm) теж витрачає вотчери на цей проєкт — закривати її
   не потрібно, якщо ліміт піднято.

Ще одна деталь: у проєкті **TypeScript 7**, де прибрано `baseUrl`, тому шляхи в
`tsconfig.json` задані відносними (`"@/*": ["./src/*"]`). Якщо колись відкотишся
на TS 5.x — це теж валідний синтаксис, міняти нічого не треба.
