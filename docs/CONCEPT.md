# Life Tracker — концепція застосунку

Персональний трекер життя: **фінанси → калорії → спорт → навчання**, зі статистикою,
аналітикою та повним експортом/імпортом даних. Локальний, без акаунтів, без сервера.

---

## 1. Принципи (що вирішує все інше)

1. **Offline-first, local-only.** Уся база — SQLite на пристрої. Ніякого логіну, ніякого
   бекенду в v1. Це різко спрощує розробку і знімає питання приватності.
2. **Швидкий ввід — головна фіча.** Якщо внести витрату/їжу довше ніж ~10 секунд —
   ти перестанеш це робити. Один екран "Quick add" + віджети/шорткати.
3. **Дані належать тобі.** JSON-бекап одним файлом + CSV по кожній таблиці (Excel/Sheets).
   Імпорт — upsert по `id`, конфлікти вирішуються по `updated_at` (last-write-wins).
4. **Схема — під аналітику, не під UI.** Кожен запис має `date` (ISO), `created_at`,
   `updated_at`, `deleted_at`, `tags`. М'яке видалення з самого початку — потім без болю
   додається синхронізація.
5. **Один кодбейс.** Mobile + desktop + (безкоштовно) web з одного репозиторію.
6. **Не будувати синк, БД продуктів і свій бекенд у v1.** Це три класичні пастки.

## 2. Варіанти технологій

### Варіант A — Expo (React Native) + SQLite + Tauri для десктопа ⭐ рекомендований

| Шар | Вибір |
|---|---|
| UI / логіка | Expo SDK 54+, TypeScript, expo-router |
| Стилі | NativeWind (Tailwind-подібно) |
| БД | `expo-sqlite` + **Drizzle ORM** (типізовані міграції) |
| Графіки | `react-native-svg` / `victory-native` (Skia) |
| Десктоп | **Tauri 2**, що обгортає Expo-web-збірку (`react-native-web`) |
| Файли | `expo-file-system`, `expo-sharing`, `expo-document-picker` |
| Захист | `expo-local-authentication` (FaceID/відпечаток) |

**Плюси:** найшвидший шлях до працюючого застосунку; величезна екосистема; тестування на
телефоні через Expo Go за секунди; web-версія фактично безкоштовна; Tauri дає десктоп-бінарник
~10 МБ (використовує системний WebView) замість ~150 МБ у Electron.

**Мінуси / увага:** SQLite на мобільному — нативний `expo-sqlite`, на десктопі — `tauri-plugin-sql`,
на web — WASM+OPFS. Тому потрібен **тонкий адаптер сховища** (один інтерфейс, три реалізації),
решта коду його не бачить. Це ~100 рядків і повністю контрольована складність.

Референси: [expo-local-first-template](https://github.com/expo-starter/expo-local-first-template),
[Expo + Tauri для mobile/web/desktop](https://www.netguru.com/blog/react-native-expo-tauri).

---

### Варіант B — Flutter + Drift (SQLite)

Один кодбейс, але **десктоп нативний з коробки** (Windows/macOS/Linux), не «обгортка».
Найкраща якість UI та продуктивність графіків (`fl_chart`).

**Мінуси:** Dart замість TypeScript. Якщо ти вже в Python/JS — це окрема мова і окреме
середовище. Web-версія існує, але слабша за Expo-web.

**Кому підходить:** якщо десктоп — рівноцінний першокласний таргет і ти готовий вчити Dart.

---

### Варіант C — PWA: React + Vite + SQLite WASM (або Dexie) + Tauri

Найлегший у сенсі «нічого не встановлювати»: сайт, який ставиться на домашній екран.
Один артефакт працює і на телефоні, і в браузері, і (через Tauri) на десктопі.
Публікація безкоштовна — просто хостинг.

**Мінуси:** iOS Safari може вичищати сховище невикористаних сайтів (частково лікується
`navigator.storage.persist()` + регулярним JSON-бекапом); немає фонових задач і нативних
віджетів; відчуття «не зовсім застосунок».

**Кому підходить:** якщо головне — швидко почати і не платити за стор-аккаунти.

---

### Варіант D — хмара + синк (Supabase / Firebase)

Не варіант для старту, а **наступний крок**. Якщо колись захочеш кілька пристроїв —
додається не переписуванням, а шаром синхронізації поверх тієї ж локальної SQLite:
**PowerSync** або **ElectricSQL**. Локальна БД залишається джерелом істини.

Ціна: акаунти, мережа, підписки, GDPR, складність конфліктів. Тому — не в v1.

---

### Варіант E — аналітика на Python (компаньйон, не альтернатива)

Оскільки вся база — це один файл SQLite, ти можеш підключити до нього Python-аналітику:
`pandas`/`polars` + Jupyter, а потім Streamlit/Dash-дашборд на комп'ютері. Це дає глибокі
звіти (кореляції, тренди, прогнози) без обмежень мобільного UI. **Рекомендую як другу фазу.**

## 3. Модель даних (SQLite)

Повний DDL: [`schema.sql`](./schema.sql).

**Довідники:** `settings`, `currencies`, `accounts`, `income_sources`, `categories`, `tags`, `goals`

**Фінанси:** `transactions` (дохід/витрата/переказ, прив'язка до рахунку, категорії,
джерела доходу, кредиту), `loans`, `loan_rate_history`, `loan_payments`, `loan_schedule`

**Тіло:** `food_catalog` (опційно, + офлайн-кеш Open Food Facts), `meal_entries`,
`workouts`, `body_metrics`

**Навчання:** `study_sessions`

**Щоденник:** `daily_checkins` (сон, кроки, настрій, енергія, вода)

Ключові рішення:
- Гроші — **в мінорних одиницях (копійках), INTEGER**, щоб не ловити float-помилки.
- `transactions.amount` у валюті рахунку + `amount_base` у базовій валюті + `fx_rate`.
- Кредит: `loans` описує умови — **джерело** (банк, МФО, магазин), дату видачі, суму
  й ставку разом із її періодом (у день / у місяць / у рік). `rate_value` + `rate_period`
  зберігають те, як ставку назвав кредитор, а `annual_rate` — ту саму ставку, приведену
  до річних (конвенція 30/360), щоб кредити можна було порівнювати одним числом і
  сортувати «найдорожчі — першими». `loan_rate_history` — зміна ставки в часі,
  `loan_payments` — фактичні погашення (платіж спершу закриває проценти, потім тіло).
- **Похідні числа не зберігаються**: залишок, набіглі проценти, прострочення й дата
  закриття рахуються з умов і платежів на будь-яку дату (`src/domain/loan-accrual.ts`),
  а не лежать у базі. Записане похідне число після першої ж правки ставки стає
  неправдою — тому в схемі його немає.
- Калорії: `meal_entries.kcal` можна ввести руками (швидко) або взяти з `food_catalog`
  за грамами/порцією. Макроси — опційні, не блокують ввід.
- Тренування й навчання — однаково: `date` + тривалість у хвилинах + тип/предмет + суб'єктивна
  оцінка (RPE / focus). Це дає змогу рахувати тижневі обсяги й порівнювати їх між собою.
- Аналітичні VIEW (`v_monthly_finance`, `v_daily_energy`, `v_weekly_load`) — щоб графіки
  будувалися одним запитом, а не складною логікою в UI.

## 4. Екрани

1. **Quick Add (FAB, центральний)** — 4 таби: 💰 Гроші · 🍎 Їжа · 🏋️ Спорт · 📚 Навчання.
   Останні використані категорії зверху, ввід суми/калорій великою клавіатурою, «ще одна».
2. **Сьогодні** — денний підсумок: витрати/дохід, kcal in/out, хвилини спорту, хвилини навчання.
3. **Аналітика** — перемикач періоду (тиждень/місяць/рік/довільно):
   - Фінанси: дохід vs витрати, по категоріях, по джерелах доходу, тренд заощаджень,
     норма заощаджень %, боргове навантаження.
   - Кредити: залишок тіла, сплачені проценти, графік vs факт, дата закриття при поточному темпі.
   - Тіло: kcal за день vs ціль, середнє за 7 днів, вага.
   - Спорт: хвилини/тиждень, по типах, RPE-тренд.
   - Навчання: години/тиждень, по предметах, серії (streaks).
   - **Кореляції** — kcal vs тренування, сон vs навчання. Це те, за що застосунок люблять.
4. **Кредити** — список із сортуванням (за річною ставкою, за боргом, за простроченням),
   картка кредиту: джерело, ставка, залишок, набіглі проценти й «скільки коштує щодня»,
   погашення з авторозбиттям на проценти/тіло, зміна ставки, графік і калькулятор
   «що якщо платити більше».
5. **Цілі** — місячні таргети: заощадити X, 12 тренувань, 20 год навчання.
6. **Налаштування** — базова валюта, цілі, нагадування, біометрія, **Бекап: Експорт / Імпорт**.

## 5. Експорт / Імпорт

- **JSON (повний бекап):** один файл `life-tracker-YYYY-MM-DD.json` з `schema_version`,
  `exported_at` і масивами по кожній таблиці. Це основна страховка і формат переносу між пристроями.
- **CSV (по таблиці):** для Excel/Google Sheets і Python-аналітики.
- **Імпорт:** upsert по `id`; якщо `updated_at` вхідного > локального — перезапис, інакше пропуск.
  Перед імпортом — автоматичний бекап поточної бази.
- **Куди зберігати:** `expo-sharing` (Google Drive, Telegram, пошта) або локальна тека.
- **Опційно:** шифрування бекапу паролем; автобекап раз на тиждень із нагадуванням.

## 6. Дорожня карта

**Фаза 0 — каркас (2–3 дні).** Expo + TS + expo-router, схема в Drizzle, міграції,
адаптер сховища для web, тестовий білд на телефон через Expo Go.

**Фаза 1 — MVP (2–4 тижні).** Рахунки, категорії, джерела доходу, транзакції;
калорії руками; тренування; навчання; екран "Сьогодні"; 3–4 базові графіки;
експорт/імпорт JSON+CSV. **На цьому етапі застосунок уже можна використовувати щодня.**

**Фаза 2 — глибина (3–4 тижні).** Кредити з графіком і процентами, каталог їжі
(сканер штрихкоду + Open Food Facts), цілі, нагадування, біометрія, кореляції,
Python/Streamlit-дашборд.

**Фаза 3 — десктоп і публікація.** Tauri-білд, іконки, безпечні зони екрана,
публікація в Play Store (можна безкоштовно) / App Store ($99/рік), або PWA-версія.

**Фаза 4 (опційно) — синк.** PowerSync/ElectricSQL + Supabase, якщо захочеться кілька пристроїв.

## 7. Що НЕ робити в v1

- Не писати власний бекенд і авторизацію.
- Не робити власну базу продуктів — брати Open Food Facts.
- Не будувати синхронізацію «про запас».
- Не намагатись автоматично тягнути банківські транзакції (в Україні це або API банку з
  договором, або scraping — окремий великий проєкт).
- Не робити 30 екранів. 6 екранів і швидкий ввід кращі за повний, але невикористовуваний застосунок.

## 8. Що з цього вже реалізовано

Каркас Фази 0 і більша частина Фази 1 зібрані в цьому ж репозиторії:

- схема SQLite (18 таблиць, 6 аналітичних VIEW) + міграції й сіди — `src/db/migrations.ts`;
- типізований CRUD на Drizzle — `src/db/schema.ts`, `src/domain/*`;
- математика кредитів (ануїтет, графік, ефект дострокового погашення) — `src/domain/loan-math.ts`;
- **кредити як повний цикл**: умови (джерело, дата, сума, ставка у день/місяць/рік),
  щоденне нарахування процентів на залишок, погашення з автоматичним розбиттям
  «проценти → тіло», прострочення, зміна ставки в часі, сортування списку за
  дорожнечею грошей — `src/domain/loan-accrual.ts`, `app/(tabs)/loans.tsx`,
  `app/loan/[id].tsx`, `app/loan/new.tsx`;
- екрани «Сьогодні», «Кредити», «Аналітика», «Налаштування» і Quick Add — `app/`;
- експорт/імпорт JSON і CSV із LWW-злиттям — `src/features/backup/`;
- 269 перевірок схеми, аналітики, кредитної математики й бекапу на справжньому
  SQLite — `scripts/verify-db.ts`.

Актуальний стан, інструкції запуску й перелік того, що ще не зроблено —
у [`../README.md`](../README.md). Цей документ залишається описом задуму й
обґрунтуванням технологічних виборів; якщо код і документ розійдуться, істина — у коді.
